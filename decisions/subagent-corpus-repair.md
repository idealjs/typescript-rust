# corpus 修复 subagent 的任务边界

## 结论

多 subagent 并行修复 corpus 失败用例时，执行以下硬约束：

1. 全量验证由主 agent 独占执行。subagent 只跑单例复现（看失败形态，用于定位根因），不跑全量 corpus 与全量 fourslash
2. subagent 必须接到明确的用例清单（worktree 根的 assigned_cases.txt），不放任自由修复
3. subagent 只负责查看逻辑与修改代码：定位根因、对照 Go 改代码、cargo check 编译通过即交付；修改是否正确由主 agent 测试裁决，不通过打回重修
4. subagent 按 hunk 粒度小步提交或以补丁交付，配合交接日志，防止平台配额终止导致进度丢失

## 否决项一：subagent 执行全量测试

否决 subagent 在收尾时跑全量 corpus（约 25 分钟）与全量 fourslash（约 20 分钟）的验证流程。

理由：

- subagent 受平台配额票据约束，会被中途终止，实测两种形态：票据过期（off-peak-ticket-expired）与 600 秒无工具活动超时。长验证跑一半被杀，验证结果作废，未提交的修复也随之丢失
- 4 个 subagent 并行各跑一轮全量，重复消耗合计小时级的 CPU，挤占内存带宽，违背宿主保留 30% CPU 余量的约束
- 全量回归的裁决收敛到主 agent 单点，职责清晰：主 agent 跑全量，发现回归再分发回对应家族的 subagent 修复

## 否决项二：只给家族不给清单

否决「你负责某家族（基线 N 例），自由发挥」式派发。

理由：

- subagent 接手后必须先自己跑家族批量定位「还剩什么没修」，批量一轮十几分钟，是修复速度慢的主要根因。清单由主 agent 从最新全量 runlog 与家族批量结果预先提取，subagent 省去这一步
- 修复面漂移：自由修复会顺手扩到清单外孤例，产出不可预测，并与并行家族改到同一源文件，合并冲突增多
- 正确做法：主 agent 把该家族当前实际剩余失败集写入 assigned_cases.txt，subagent 只修清单内用例。发现清单外系统性根因时上报主 agent 裁决，不自行扩大修复面

## 否决项三：subagent 自行验证修复正确性

否决 subagent 在交付前跑清单批量或全量确认「转绿数/零回归」。

理由：

- 每轮清单批量 5 到 10 分钟，一个 subagent 一轮工作要跑多轮批量验证，是修复速度慢的另一半根因
- subagent 受配额票据约束随时被终止，验证跑到一半结果作废；而验证结论（转绿数）只对主 agent 的合并决策有意义
- 正确性裁决收敛到主 agent：subagent 交付代码加逻辑说明，主 agent 跑单例与清单批量测试，不通过打回指定 subagent 重修，形成修改与验证的分离闭环

## 配额终止的应对

subagent 运行中会被平台终止（票据过期或长时间无工具活动），危害是未提交改动全部丢失，继任者重复劳动。三条解法同时使用：

- 小步提交：每个 5 到 20 例的验证单元，家族批量净绿且编译通过即提交，不等收尾验证。被终止时已提交进度全部保留
- 交接日志：worktree 根的 progress_notes.md 记录已修簇、已试失败簇、剩余簇，不入版本库，继任者第一步读它
- 长命令后台化：预计超过 3 分钟的命令后台运行并重定向到日志，随后每 30 到 60 秒轮询一次输出，避免触发无活动超时
